# GChat MCP

Работай опубликованными инструментами MCP GChat. Схему builder сохраняй одним из двух способов: небольшую — напрямую через `automation_schema_update`, крупную — через [HTTP-загрузку JSON](references/schema-file-upload.md) и `automation_schema_update_from_upload`. Для загрузки подойдёт любой клиент, способный отправить multipart HTTP-запрос с тем же MCP Bearer; доступ к Codex CLI не требуется. Токен определяет организацию: не передавай `organization_id` и не вызывай остальные HTTP API вместо MCP. Ошибку авторизации, валидации или отсутствующий ресурс не трактуй как пустой результат.

## Правила для любой задачи GChat

- Каталог MCP `tools/list` может быть постраничным: при поиске инструмента проходи все страницы по `nextCursor`. Отсутствие инструмента на первой странице не означает, что он недоступен. Подробности — в [каталоге инструментов](references/tools.md#пагинация-каталога-mcp).
- Для побочных действий сначала найди точный ресурс и сверь его имя; не выбирай его только по месту в списке и не угадывай UUID.
- Если поиск MCP не охватывает нужный тип ресурса, используй ID из уже прочитанной схемы или попроси его у пользователя.
- Различай внешнее событие автоматизации и шаговый trigger внутри `node.data.triggers[]`.
- Не отправляй тестовые сообщения реальным клиентам без прямой просьбы пользователя.
- Не называй сохранённую автоматизацию рабочей, пока не перечитал схему и не проверил её состояние включения.

## Обязательный порядок при создании или изменении схемы

1. Определи внешний триггер автоматизации отдельно от внутренних `data.triggers[]`.
2. Перед проектированием прочитай три обязательных справочника выше: контракт, layout и короткие примеры. По каждому типу используемого блока/триггера открой его профильную ссылку из таблицы.
3. Для существующей автоматизации получи актуальную ревизию и полную схему через `automation_schema_get`, если ответ помещается в лимит клиента. Для крупной схемы используй актуальный полный исходник и ревизию из `automation_get`; если полного исходника нет, не заменяй существующую схему частичной копией. Сохрани все несвязанные ветви и узлы.
4. Сначала спроектируй пути и точки схождения, потом расставь узлы. Ветви связывай с конкретными trigger- или block-портами; координаты не заменяют рёбра.
5. Проверь уникальность ID, корректность всех `sourceHandle`, объявление используемых переменных, назначение каждого шага, ожидаемые конечные точки и отсутствие случайно изолированных узлов. У каждого ребра из `step` должен быть непустой handle, совпадающий с реальным выходом; `null` допустим только для ребра из `start`. Для безусловного перехода между шагами добавь внутренний `goto` и используй `step-trigger:<trigger.id>`. Для новых координат используй сетку `20 × 20`, оценивай высоты по [фактической раскладке frontend](references/builder/layout.md#оценка-высоты-step-узлов), оставляй не менее `40 px` между границами рабочих узлов и рамками note и соблюдай поля note.
6. Обновление схемы заменяет объект целиком. Для небольшой схемы передай объект `schema` в `automation_schema_update`; для крупной загрузи этот же объект как JSON-файл и вызови `automation_schema_update_from_upload`. Не передавай экспортную обёртку. После записи проверь ревизию и схему доступным для её размера способом.
7. Включай автоматизацию отдельным вызовом, только если пользователь просит активный сценарий. Успешное сохранение или включение не доказывает, что вся логика выполнится; реальное тестирование делай только контролируемо и по прямой просьбе.

Для триггеров, блоков, переменных, выражений и ограничений исполнения используй точные контракты профильных references. Не заменяй их догадками по названиям полей, тексту старого экспорта или успешному ответу API.
