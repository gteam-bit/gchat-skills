## Форма схемы

`automation_schema_update` принимает сам объект схемы в `schema`. Не оборачивай его в export-контейнер с `format`, `source`, `references` или `exported_at`.

```json
{
  "version": 2,
  "variables": { "env": [], "funnel": [] },
  "nodes": [
    {
      "id": "start",
      "type": "start",
      "position": { "x": 0, "y": 0 },
      "data": {}
    },
    {
      "id": "step-entry",
      "type": "step",
      "position": { "x": 320, "y": 0 },
      "data": { "title": "Начало", "blocks": [], "triggers": [] }
    }
  ],
  "edges": [
    {
      "id": "edge-start-entry",
      "source": "start",
      "target": "step-entry",
      "sourceHandle": null,
      "targetHandle": null,
      "type": "step"
    }
  ]
}
```

Формат схемы использует `version: 2`. Отдельный `expected_schema_version` в MCP-вызове — ревизия сохранённой схемы, а не формат. Для существующей схемы версии 2 нельзя откатывать `version` до 1.

Экспортированный JSON может содержать обёртку `format`, `exported_at`, `source`, `funnel`, `schema` и `references`. Для `automation_schema_update` передавай только объект из поля `schema`; метаданные экспорта не входят в контракт обновления.

Начальный узел один, типа `start`. Узлы `step` хранят `data.title`, `data.blocks[]` и `data.triggers[]`. Узел `note` — только визуальная заметка; не соединяй с ним рёбра. У всех узлов и рёбер должны быть уникальные ID, а концы ребра должны ссылаться на существующие узлы.

При чтении пустой `data` стартового узла MCP может вернуть как `{}`, так и `[]`; трактуй оба варианта как пустые данные. Схему шага сохраняй объектом с обязательными массивами `blocks` и `triggers`.

## Порты и соединения

`sourceHandle` вычисляется из источника выхода:

- стартовый узел: `null`;
- шаговый триггер: `step-trigger:<trigger.id>`;
- маршрут `ai_router`: `block-port:ai_router:<block.id>:<route.key>`;
- кнопка с действием `transition`: `block-port:<block.type>:<block.id>:<button.key>`.

`sourceHandle: null` допустим только у ребра из `start`. У каждого ребра из `step` должен быть непустой handle, соответствующий реальному выходу этого шага: его триггеру, маршруту или кнопке-переходу. Если шаг должен просто продолжить выполнение в один следующий шаг и подходящего выхода ещё нет, добавь в `data.triggers[]` триггер `goto` и укажи `step-trigger:<goto.id>` в ребре. Не создавай ребро из `step` с `sourceHandle: null`.

Один выход может иметь не более одного исходящего ребра. Незаведённый выход завершает ветку. Для сценария с ветвлением обычно соединяй и основную, и fallback/иначе ветки.

Внешнее событие запуска задаётся метаданными `automation_create`/`automation_update` (например, `message.received`). `any_message`, `timeout`, `condition` и другие типы в `data.triggers` — внутренние выходы шагов, а не внешние триггеры автоматизации. Подробности — в [триггерах и условиях](builder/triggers-and-conditions.md).

## Сохранение схемы

1. Найди и проверь нужные `space_id` и `automation_id` через MCP.
2. Вызови `automation_schema_get` и возьми возвращённый `schema_version` как `expected_schema_version`. `schema: null` означает, что схему нужно построить.
3. Передай полную схему: обновление заменяет её целиком.
4. При конфликте ревизии перечитай схему и перенеси намеренные изменения на свежую версию.
5. После успешного обновления снова прочитай схему и проверь ветки, ID и значения.
6. Включай автоматизацию отдельным вызовом только если пользователь просит активный рабочий сценарий.

## Граница валидации

Backend проверяет структуру графа и отдельные типы полей, но глубина проверок различается по блокам и триггерам. Например, часть ссылок и форматов проверяется при сохранении, а некоторые пустые/неверные значения обнаруживаются лишь executor'ом при запуске. Статус `200` у обновления и успешный `automation_enable` не являются доказательством корректного runtime-ветвления.

Перед включением сверяй каждый используемый блок и триггер с его профильным файлом. ID медиа, моделей и базы знаний бери только из прочитанной схемы или от пользователя: текущий MCP не предоставляет для них справочник. Для безопасной проверки реального поведения используй контролируемый тестовый чат по явной просьбе пользователя или читай trace уже выполненного запуска; не тестируй на случайном клиенте.
